## 1. אבטחה

### 1.1 🔴 מתאמן יכול להפוך את עצמו למנהל

**מה קורה:** המדיניות `profiles_write` ב-`supabase/schema.sql` מרשה לכל משתמש מחובר לעדכן את השורה שלו — **כל עמודה**, כולל `is_admin`. ב-Postgres אין הגבלת עמודות ב-RLS, ו-Supabase נותן ל-`authenticated` הרשאת UPDATE על כל הטבלה כברירת מחדל. בקשת PATCH אחת עם ה-JWT של המתאמן (`{"is_admin": true}`) — ומאותו רגע `is_admin()` מחזירה true: קריאה של כל ה-states וה-board, מחיקת משתמשים, איפוס סיסמאות, איפוס בלוק, כתיבת התוכנית המשותפת.

**מה לא:** אף קוד באפליקציה לא כותב `is_admin` (רק קורא). הסיכון הוא מתאמן (או מי שגנב לו סשן) שפותח את כלי הפיתוח. עם 7 מתאמנים מוכרים הסיכוי נמוך — אבל התיקון הוא עשר שורות.

**תיקון (מוכן להרצה; נכנס ל-`schema.sql` באישור אורי):** טריגר שמסרב לשינוי `is_admin` מבקשות API אלא אם המבקש כבר מנהל. עורך ה-SQL (תפקיד `postgres`) לא נחסם, כך שההנחיה ב-README ("הפוך את עצמך ל-admin") ממשיכה לעבוד.

```sql
create or replace function public.guard_profile_flags()
  returns trigger
  language plpgsql
  set search_path = public
as $$
begin
  -- API callers run as `authenticated` (or `anon`); the SQL editor runs as `postgres` and passes.
  if current_user in ('anon', 'authenticated') and not public.is_admin() then
    if tg_op = 'INSERT' and coalesce(new.is_admin, false) then
      raise exception 'is_admin is read-only';
    end if;
    if tg_op = 'UPDATE' and new.is_admin is distinct from old.is_admin then
      raise exception 'is_admin is read-only';
    end if;
  end if;
  return new;
end;
$$;
drop trigger if exists profiles_guard_flags on public.profiles;
create trigger profiles_guard_flags
  before insert or update on public.profiles
  for each row execute function public.guard_profile_flags();
```

**לאמת לפני ואחרי** (SQL Editor): `select name, is_admin from public.profiles order by is_admin desc;` — רק אורי אמור להיות true.

## 5. סנכרון, בק-אנד וביצועים

### 5.1 בריאות המכשירים בפאנל (M)

- **גרסת האפליקציה לכל מתאמן:** `pub` יישא את `BUILD` — הפאנל יראה מי תקוע על קוד ישן (היום מנחשים מהלוגים).
- **דיווח שגיאות מהמכשירים:** טבלת `client_errors` (הכנסה בלבד, RLS לבעלים, מוגבלת קצב) — `window.onerror`, דחיפות שנכשלו, "interceptor לא פעיל". תצוגת "🩺 בריאות" בפאנל. תחליף זול לשירות ניטור חיצוני, בלי CDN נוסף.

### 5.2 הבלוב מכיל את התוכנית (L 🔒, בלוק 3)

כל שורת `states` נושאת את טקסט התוכנית של המתאמן (~170KB לבלוב מלא בבלוק 1), וכל boot מושך אותה. שמירה שוטפת כבר עברה לימים בלבד (v3). הצעד הבא — לשמור בענן רק רישומים + חותמות, והתוכנית מגיעה מהקוד/מהשרת — נוגע במיזוג, בנרמול ובחוקי הברזל 1-5. לעשות רק עם סביבת בדיקות (§6.3) ורק בין בלוקים.

### 5.3 תקרות Supabase (חינמי)

- **השהיה אחרי 7 ימים ללא פעילות** — פרויקט חינמי מושהה, וההתחברות נכשלת עד שמעירים אותו מהדשבורד. בין בלוקים (תחזוקה ארוכה) זה סיכון אמיתי; פתיחת הפאנל פעם בשבוע מספיקה.
- Egress 5GB/חודש, 500MB מסד — רחוק מהתקרה; הארכיון גדל ~2.5MB לבלוק. בדיקה חודשית כבר ברשימה.
- גיבוי יומי + PITR רק ב-Pro (25$) — התזכורת בפאנל מכסה; לשקול ב-50+ מתאמנים.

### 5.4 דומיין משלנו (S)

`crossfit-bat-yam-capacity.vercel.app` → למשל `capacity.crossfitbatyam.co.il`. הקישור שהמתאמנים התקינו לא ישתנה גם אם נחליף אחסון. דורש דומיין בבעלות אורי.

## 6. איכות, בדיקות ותהליך

### 6.1 בדיקות אוטומטיות למיזוג (M)

`mergeTrackers`, `stampChangedDays`, `cleanLog`/`logSig` ו-`push_days` הם הקוד שגרם לכל אובדני הנתונים. היום אין אף בדיקה. הצעה: לחלץ את הפונקציות הטהורות לבדיקה (ללא שינוי בהתנהגות) + קובץ בדיקות על תרחישי העבר (שני מכשירים, אופליין → אונליין, שורה נעלמה, אחסון מת). **איפה זה רץ:** במחשב הזה אין Node (CLAUDE.md, 10/09) — או דף בדיקה שנפתח בדפדפן (בלי התקנה, רץ גם דרך חלון הדפדפן של קלוד), או התקנת Node (חינמי, הכרעת אורי). נחליט כשמגיעים לפריט.

### 6.2 סקריפט "לפני דיפלוי" (S)

בודק ב-3 שניות: `BUILD` == `version.json`; `BLOCK` == `BLOCK_NUM`; `PROGRAM_VERSION` עלה אם `programWeekN` השתנה; כל הקבצים LF; כרטיס הסיכום ב-app.html זהה ל-`design/`; אין `.select()` על upsert של states (חוק ברזל 1). רץ ידנית או כ-hook לפני commit. משלים את הזרימה הידנית ב-`release.md` §3 (אימות מול הפרודקשן אחרי הפריסה נשאר כמו שהוא).

### 6.3 סביבת בדיקות (M)

פרויקט Supabase שני (חינמי) + ענף `staging` שמקבל כתובת preview ב-Vercel, ו-`supa-config.js` שבוחר פרויקט לפי הדומיין. בדיקות סנכרון עם שני מכשירים בלי לגעת בפרודקשן ובלי משתמש בדיקה שצריך למחוק. פותח את הדלת ל-5.2 ול-4.1.

### 6.4 קצב והגדרת "גמור"

- שיפור אחד לדיפלוי, באמצע השבוע (לא ראשון — יום המבחן, לא שישי — יום הסבבים).
- "גמור" = בדיקה ב-`?dev=1` + בטלפון של אורי + רשומה ביומן + עדכון מסמך התחום. גרסה — אורי נוקב.
- המסמך הזה = הרשימה היחידה. כל שאלה שנסגרת עוברת ל-§9 עם תאריך.
- **ארכיטקטורת הקבצים (10/09):** כל אזור חדש ב-`app.html`/`boot.js` מקבל עוגן (`// ---- שם ----`) כדי ש-`tools/map.py` ימצא אותו; קוראים סקשן אחד, לא קובץ; רשומת יומן עד ~10 שורות; בלי מספרי שורות במסמכים (CLAUDE.md 💰).
